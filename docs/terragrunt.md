# Terragrunt client guide

Client projects consume the modules from this repository **exclusively through
Terragrunt**. They do not copy or maintain local modules.

## Contract between the modules and the client

The source modules:

- contain **no backend block** (state configuration is generated by Terragrunt);
- contain **only `required_providers`** in their `versions.tf` (no endpoint,
  no credentials, no SSH configuration);
- do **not** read upstream state with `terraform_remote_state`;
- receive upstream values as **input variables** (`zones`, `vnets`, `bridges`,
  `os_images`, `lxc_templates`, ...);
- do **not** embed cloud-init templates.

The client project is responsible for:

- the state backend;
- the provider configuration;
- the pinned module version (Git tag);
- the cloud-init templates and their directory.

## Pinned Git tags (mandatory)

Every `terraform.source` must reference an immutable tag:

```hcl
terraform {
  source = "git::https://example.com/org/pdcs-core-tf-modules.git//01-foundation?ref=v1.0.0-rc1"
}
```

Never use `main`, `master`, a branch or a floating ref in a client project. A
client stays on its tag until its author deliberately bumps it. The tag lives
in each unit's `terraform.source` and is updated explicitly:

```hcl
# 01-foundation/terragrunt.hcl
terraform {
  source = "git::https://example.com/org/pdcs-core-tf-modules.git//01-foundation?ref=v1.1.0"
}
```

Publishing a new version from the modules repository:

```shell
git tag -a v1.0.0 -m "pdcs-core-tf-modules v1.0.0"
git push origin v1.0.0
```

## Target client layout

```
my-client-project/
├── root.hcl                      # generated backend + provider
├── 01-foundation/
│   └── terragrunt.hcl            # source .../01-foundation?ref=v1.0.0-rc1
├── 02-networking/
│   └── terragrunt.hcl            # depends on 01-foundation
├── 03-compute/
│   ├── terragrunt.hcl            # depends on 01-foundation + 02-networking
│   └── cloud-init-templates/     # CLIENT-OWNED templates
└── ...
```

The units map to the three modules and are applied in this order:

```
01-foundation -> 02-networking -> 03-compute
```

Terragrunt enforces the order through `dependency` blocks, so
`terragrunt run --all apply` is safe.

## `root.hcl`: backend and provider

`root.hcl` is included by every unit:

```hcl
include "root" {
  path = find_in_parent_folders("root.hcl")
}
```

### Backend generated client-side

The modules contain no backend. Terragrunt generates it per unit:

```hcl
remote_state {
  backend = "local"
  generate = {
    path      = "backend.tf"
    if_exists = "overwrite_terragrunt"
  }
  config = {
    path = "${get_terragrunt_dir()}/terraform.tfstate"
  }
}
```

For a shared or CI-friendly state, replace `local` with a remote backend
(for example S3, HTTP or GCS). See `examples/terragrunt-client/root.hcl` for a
ready-to-edit example. Changing the backend only affects the client project;
the modules are untouched.

### Provider generated client-side

The modules only declare `required_providers`. The actual provider block is
generated by Terragrunt:

```hcl
generate "provider" {
  path      = "provider.tf"
  if_exists = "overwrite_terragrunt"
  contents  = <<-EOF
    provider "proxmox" {
      insecure = true
      ssh {
        agent    = true
        username = "root"
        node {
          name    = "pve"
          address = "pve.example.com"
        }
      }
    }
  EOF
}
```

Do not redeclare `required_providers` in the generated file: the module source
already declares them. A second `required_providers` block in the same root
module is rejected by OpenTofu.

Credentials are read by the `bpg/proxmox` provider from the environment:

```shell
export PROXMOX_VE_ENDPOINT="https://pve.example.com:8006"
export PROXMOX_VE_API_TOKEN='root@pam!token=...'
```

## Dependencies between units

Upstream outputs are passed explicitly. There is no hidden remote-state read
inside the modules.

```hcl
# 02-networking/terragrunt.hcl
dependency "foundation" {
  config_path = "../01-foundation"

  mock_outputs = {
    zones              = { DMZ = "DMZ", LAB = "LAB" }
    zones_config       = "{}"
    controllers_config = "{}"
  }
  mock_outputs_allowed_terraform_commands = ["validate", "plan"]
}

inputs = {
  zones              = dependency.foundation.outputs.zones
  zones_config       = dependency.foundation.outputs.zones_config
  controllers_config = dependency.foundation.outputs.controllers_config
  # ...
}
```

```hcl
# 03-compute/terragrunt.hcl
dependency "foundation" {
  config_path = "../01-foundation"
  # ...
}

dependency "networking" {
  config_path = "../02-networking"
  # ...
}

inputs = {
  vnets         = dependency.networking.outputs.vnets
  bridges       = dependency.foundation.outputs.bridges
  os_images     = dependency.foundation.outputs.os_images
  lxc_templates = dependency.foundation.outputs.lxc_templates
  # ...
}
```

## Cloud-init templates: client-owned

Cloud-init templates are **not shipped with the base modules**: they are
environment-specific (users, SSH keys, packages, bootstrap scripts) and would
make the modules non-portable. The complete rules are in
[cloud-init.md](cloud-init.md).

Each client project defines its own directory:

```
my-client-project/
└── 03-compute/
    ├── terragrunt.hcl
    └── cloud-init-templates/
        └── ubuntu-bastion.yaml.tftpl
```

and passes it to the compute module:

```hcl
inputs = {
  cloud_init_templates_dir = "${get_terragrunt_dir()}/cloud-init-templates"

  virtual_machines = {
    "bastion-01" = {
      # ...
      cloud_init = {
        snippet_datastore = "snippets"
        init_datastore    = "images"
        template_file     = "ubuntu-bastion.yaml.tftpl"
        ssh_keys          = ["ssh-ed25519 AAAA... user@example"]
      }
    }
  }
}
```

The `template_file` value is resolved relative to
`cloud_init_templates_dir` (or used as-is when absolute).

For module development only, copies of the reference templates are kept in
`03-compute/examples/test-local/cloud-init-templates/`. They are **not**
part of the module interface.

## Running the client

```shell
# Using the Docker wrapper from this repository
./terragrunt-docker.sh examples/terragrunt-client run --all plan
./terragrunt-docker.sh examples/terragrunt-client run --all apply

# Or with Terragrunt installed locally
cd examples/terragrunt-client
terragrunt run --all plan
terragrunt run --all apply
```

Useful commands:

```shell
terragrunt run --all validate          # validate every unit
terragrunt run --all plan              # plan, ordered by dependencies
terragrunt --working-dir 01-foundation output zones
terragrunt --working-dir 03-compute output vm_ids
```

## Version bump procedure (client side)

1. Read the modules changelog / diff between the current tag and the target tag.
2. Update the `?ref=` value in the three unit `terraform.source` blocks
   (`01-foundation`, `02-networking`, `03-compute`).
3. Run `terragrunt run --all plan` and review the changes.
4. Apply unit by unit (`01-foundation`, then `02-networking`, then
   `03-compute`) or with
   `run --all apply`.

No client project is ever forced to upgrade: `v1.0.0` keeps working even when
the modules repository moves on.
