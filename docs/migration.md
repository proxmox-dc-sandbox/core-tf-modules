# Migration from the legacy repository

The previous provisioning tree (`to-dc-provisionner/`) contained three
environment-specific root modules, shared building blocks, per-environment
`tfvars`, and documentation. This repository turns the same resources into
versioned source modules for Terragrunt.

The legacy tree is a reference only. It is excluded from version control and
must not be committed.

## Layout mapping

| Legacy | New |
|---|---|
| `01-foundation/` (root module with backend and provider) | `01-foundation/` source module + `examples/test-local` + client unit |
| `02-networking/` (read foundation state) | `02-networking/` module with explicit `zones` inputs |
| `03-compute/` (read 01 and 02 states) | `03-compute/` module with `vnets`, `bridges`, `os_images` inputs |
| `modules/proxmox-vm`, `sdn-zone`, `sdn-vnet` | Unchanged under `modules/` |
| `modules/storage-roles` | Absorbed into `modules/storage-resolution` (breaking: the standalone module is gone; the layers' `storage_roles` input is unchanged) |
| `cloud-init-templates/` | Client-owned `03-compute/cloud-init-templates/`; development copies in the compute example |
| `envs/<env>/*.tfvars` | Client Terragrunt units (one state per layer) |
| `providers.tf` with connection settings | `versions.tf` with `required_providers` only |
| `backend.tf` in each layer | Generated by Terragrunt `remote_state` |
| `docker/` OpenTofu image | OpenTofu + Terragrunt image |
| `docs/*.md` | Reorganized under `docs/` |

## Behaviour changes

### No backend or provider configuration in modules

A module must work with any client backend and any credentials source. State and
provider configuration are generated by the client project. See
[terragrunt.md](terragrunt.md).

### Upstream values are explicit inputs

The modules no longer use `terraform_remote_state`. Terragrunt `dependency`
blocks read upstream unit outputs and pass them as inputs. This keeps the module
contract visible and testable.

### Cloud-init templates are client-owned

Templates are not part of the module interface. The client project owns its
templates and passes `cloud_init_templates_dir` to the compute module. See
[cloud-init.md](cloud-init.md).

### Numbered modules and shared blocks

The base modules are numbered (`01-foundation`, `02-networking`,
`03-compute`). Reusable building blocks live in `modules/`.

### Immutable versions

Client units pin a Git tag (`?ref=v1.0.0-rc1`). The `main` branch is for development.

## What was intentionally not migrated

- `NOTES.md`: contained environment-specific access information and an API
  token. Secrets are never copied into this repository.
- Legacy `SESSION_REPORT.md`: internal working notes.
- Environment-specific `envs/*.tfvars`: these become client project
  configuration.
- The legacy debug scenario: sanitized and published as
  [case-studies/evpn-routing.md](case-studies/evpn-routing.md).

## Migration procedure for an existing deployment

1. Create a client project with `root.hcl`, `01-foundation`, `02-networking`
   and `03-compute` units. Use [examples/terragrunt-client](../examples/terragrunt-client)
   as a starting point.
2. Move the existing `tfvars` values into the corresponding unit `inputs`.
3. Configure the client backend and provider in `root.hcl`.
4. Copy the cloud-init templates into the client `03-compute/cloud-init-templates/`.
5. Pin a released tag in each `terraform.source`.
6. Run `terragrunt run --all plan`. If the resources already exist, either:
   - re-create the datacenter from the new client project; or
   - import the existing resources into the new unit states:
     ```shell
     terragrunt --working-dir 01-foundation run -- import '<address>' '<id>'
     terragrunt --working-dir 02-networking run -- import '<address>' '<id>'
     terragrunt --working-dir 03-compute run -- import '<address>' '<vmid>'
     ```
7. Apply the layers in order and verify the plan.

The migration can be progressive: keep the legacy environment running while the
new client project is validated, then switch.
