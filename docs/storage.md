# Storage selection: by name or by role

Every place that accepts a datastore supports two forms:

```hcl
# 1. By name: a real cluster datastore ID, used as-is
datastore = "local-lvm"

# 2. By role: a logical name resolved from datastore capabilities
datastore = "images"
```

Resolution rules (`modules/storage-resolution`):

1. If the reference matches a real datastore ID on the node, it is used as-is.
2. Otherwise, if it matches a role defined in `storage_roles`, the role is
   resolved (automatically by content type, or pinned with `datastore = ...`).
3. Otherwise, the plan fails with a clear message listing available datastores
   and their content types.

A real name always wins. Defining roles does not change references that already
match a real datastore.

## Datastore, content type and role

| Concept | Definition | Examples |
|---|---|---|
| Datastore | A real cluster storage (name, type, capabilities) | `local`, `local-lvm`, `ceph-vms`, `truenas-iso` |
| Content type | What a datastore accepts | `iso`, `vztmpl`, `snippets`, `images`, `rootdir`, `backup`, `import` |
| Role | A logical requirement = the content types a resource needs | `iso` -> `["iso"]`, `images` -> `["images"]`, `rootdir` -> `["rootdir"]` |

Role names are arbitrary. Use the vocabulary of your infrastructure:

```hcl
storage_roles = {
  "os-images"  = { content = ["iso"] }
  "vm-disks"   = { content = ["images"], datastore = "ceph-vms" }
  "ct-rootfs"  = { content = ["rootdir"] }
  "cloud-init" = { content = ["snippets"] }
  "lxc-tpl"    = { content = ["vztmpl"] }
}
```

Constraints:

- the same role name must be used in its definition and in the resource that
  references it;
- the role content types must cover the need of the resource (VM disk ->
  `images`, snippet -> `snippets`, cloud image -> `iso`, ...).

Resource requirements:

| Resource | Field | Required content type |
|---|---|---|
| Cloud image / ISO (`os_images`) | `datastore` | `iso` (or `import` for qcow2) |
| LXC template (`lxc_templates`) | `datastore` | `vztmpl` |
| Cloud-init snippet | `cloud_init.snippet_datastore` | `snippets` |
| cloud-init ISO generated by Proxmox | `cloud_init.init_datastore` | `images` |
| VM disk (`disks[].storage`) | `storage` | `images` |
| Container rootfs | `storage` | `rootdir` |

## Typical backend capabilities

| Backend | Usual content types | Notes |
|---|---|---|
| `dir` (e.g. `local`) | `iso`, `vztmpl`, `snippets`, `backup`, `import` (+ `images` if enabled) | The only backend that usually hosts snippets, ISOs and templates |
| `lvmthin` (e.g. `local-lvm`) | `images`, `rootdir` | VM/CT disks; not for ISOs or snippets |
| Ceph / RBD | `images`, `rootdir` | Distributed block storage for VM/CT disks |
| NFS | `iso`, `vztmpl`, `snippets`, `backup`, `import` | Good for images, templates and snippets; avoid VM disks for performance |

A common mistake is to host cloud images (content type `iso`) on an `lvmthin`
storage (`images`, `rootdir` only). The download fails because the datastore
does not support the content type.

## Example: Ceph + NFS cluster

Assume:

- `ceph-vms` (RBD): VM and container disks;
- `truenas-iso` (NFS): ISOs, templates, snippets, backups;
- `local`: node-local fallback.

### By name

```hcl
os_images = {
  "ubuntu-2404-cloudinit" = {
    node      = "pve"
    datastore = "truenas-iso"
    url       = "https://cloud-images.ubuntu.com/noble/current/noble-server-cloudimg-amd64.img"
    file_name = "noble-server-cloudimg-amd64.img"
  }
}

virtual_machines = {
  "bastion-01" = {
    # ...
    cloud_init = {
      snippet_datastore = "truenas-iso"
      init_datastore    = "ceph-vms"
      template_file     = "ubuntu-bastion.yaml.tftpl"
    }
    disks = {
      "scsi0" = { storage = "ceph-vms", size = 20 }
    }
  }
}
```

Advantages: deterministic placement. Drawback: every reference must be updated
when a datastore name changes.

### By role

```hcl
# 01-foundation inputs (and 03-compute inputs)
storage_roles = {
  "iso"      = { content = ["iso"] }                          # auto -> truenas-iso
  "vztmpl"   = { content = ["vztmpl"] }                       # auto -> truenas-iso
  "snippets" = { content = ["snippets"] }                     # auto -> truenas-iso
  "images"   = { content = ["images"], datastore = "ceph-vms" }
  "rootdir"  = { content = ["rootdir"], datastore = "ceph-vms" }
}

os_images = {
  "ubuntu-2404-cloudinit" = {
    node      = "pve"
    datastore = "iso"
    # ...
  }
}

virtual_machines = {
  "bastion-01" = {
    # ...
    cloud_init = {
      snippet_datastore = "snippets"
      init_datastore    = "images"
    }
    disks = {
      "scsi0" = { storage = "images", size = 20 }
    }
  }
}
```

Advantages: the same configuration works across clusters with different
datastore names. The role mapping is centralized in `storage_roles`. Drawback:
the physical datastore selected by an automatic role is less obvious; use the
`storage_roles` output to inspect it.

### Hybrid (recommended)

Use automatic roles for non-critical resources and pin performance-sensitive
ones:

```hcl
storage_roles = {
  "iso"      = { content = ["iso"] }
  "vztmpl"   = { content = ["vztmpl"] }
  "snippets" = { content = ["snippets"] }
  "images"   = { content = ["images"], datastore = "ceph-vms" }
  "rootdir"  = { content = ["rootdir"], datastore = "ceph-vms" }
}
```

## Changing a role target or storage capabilities

To change which datastore a role resolves to, edit `storage_roles` and apply. No
node-side change is required.

To change the content types of an existing storage:

- **Outside OpenTofu:** Datacenter -> Storage -> select the storage -> Content.
- **With OpenTofu:** declare the storage in `storages` in `01-foundation` and
  import it once, then manage `content` from the configuration.

After a capability change, automatic role resolution can select a different
datastore.

## Inspecting resolution

From the foundation example:

```shell
cd 01-foundation/examples/test-local
tofu output datastore_catalog   # node -> datastore -> content types
tofu output storage_roles       # node -> role -> resolved datastore
```

From a client project:

```shell
terragrunt --working-dir 01-foundation output datastore_catalog
terragrunt --working-dir 01-foundation output storage_roles
```

When a role cannot be resolved, the plan fails with the list of available
datastores and their content types.

## Decision tree

```
Is the storage placement a deliberate decision (performance, compliance)?
├─ Yes -> use the real datastore name
└─ No  -> must the configuration work across clusters?
         ├─ Yes -> use a role (pin it when determinism matters)
         └─ No  -> use a name or a role
```

## Importing an existing storage

`storages` only creates storages: the API refuses to adopt an existing ID.
To manage the content types of a storage that already exists, declare it and
import it once:

```shell
# 1. Declare it in the foundation inputs (same type/path/content).
# 2. Import it into the state:
tofu -chdir=01-foundation/examples/test-local import \
  'proxmox_storage_directory.this["local"]' local

# 3. Adjust `content`, then apply.
```

With a client project, run the import inside the foundation unit:

```shell
terragrunt --working-dir 01-foundation run -- import \
  'proxmox_storage_directory.this["local"]' local
```

Do not remove an imported storage from the configuration without a `state rm`:
OpenTofu would otherwise destroy the real storage.
