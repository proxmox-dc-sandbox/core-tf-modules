# Proxmox Datacenter Modules

[![validate](https://github.com/proxmox-dc-sandbox/core-tf-modules/actions/workflows/validate.yml/badge.svg)](https://github.com/proxmox-dc-sandbox/core-tf-modules/actions/workflows/validate.yml)

Reusable OpenTofu modules for provisioning a Proxmox VE datacenter. Client
projects consume the modules through **Terragrunt** and pin them to immutable
Git tags, so upstream changes never break a deployed project.

The stack is split into three independent layers:

```
01-foundation  ->  02-networking  ->  03-compute
```

Each layer owns a separate state, exposes a small set of outputs, and consumes
upstream values explicitly. The modules contain no backend and no provider
configuration: both are generated by the client project.

## Design goals

- **Small blast radius.** Underlay, network and tenant changes are planned and
  applied independently.
- **Reusable source modules.** Client projects do not maintain local copies of
  the modules; they reference a tagged Git revision.
- **Explicit contracts.** Upstream values are passed as input variables, not
  hidden inside `terraform_remote_state`.
- **Client-owned configuration.** Credentials, state backend, provider setup and
  cloud-init templates belong to the client project.
- **Reproducible versions.** Every client unit pins `?ref=vX.Y.Z`; upgrades are
  deliberate.

## Architecture

| Layer | Responsibility | Main inputs | Main outputs |
|---|---|---|---|
| `01-foundation` | Linux bridges, SDN zones, controllers, OS images, LXC templates, storages, storage roles | node/storage definitions | `zones`, `bridges`, `os_images`, `lxc_templates`, `storage_roles` |
| `02-networking` | SDN vnets, subnets, SDN apply | foundation zone outputs, vnet/subnet definitions | `vnets`, `subnets` |
| `03-compute` | VMs (cloud-init, ISO, golden clone) and LXC containers | foundation and networking outputs, client cloud-init templates | `vm_ids`, `vm_vmid`, `vm_ipv4_addresses`, `container_ids` |

Shared building blocks live in `modules/`: `proxmox-vm`, `sdn-zone`,
`sdn-vnet` and `storage-resolution`.

See [docs/architecture.md](docs/architecture.md) for the full contracts and
data flow.

## Quick start

### Module development

Every layer ships a self-contained example with its own provider and local
backend:

```shell
cd 01-foundation/examples/test-local
cp terraform.tfvars.example terraform.tfvars
tofu init
tofu plan

cd ../../../02-networking/examples/test-local
cp terraform.tfvars.example terraform.tfvars
tofu init
tofu plan

cd ../../../03-compute/examples/test-local
cp terraform.tfvars.example terraform.tfvars
tofu init
tofu plan
```

Apply the layers in order. See [docs/getting-started.md](docs/getting-started.md)
for prerequisites and details.

### Client project

A client project contains one Terragrunt unit per layer:

```hcl
# 01-foundation/terragrunt.hcl
terraform {
  source = "git::https://example.com/org/pdcs-core-tf-modules.git//01-foundation?ref=v1.0.0-rc1"
}
```

The reference project in
[examples/terragrunt-client](examples/terragrunt-client) includes a generated
backend and provider, dependency wiring and client-owned cloud-init templates.

```shell
./terragrunt-docker.sh examples/terragrunt-client run --all plan
```

See [docs/terragrunt.md](docs/terragrunt.md) for the complete client guide.

## Development

Requirements: OpenTofu >= 1.8, `bpg/proxmox` >= 0.70. Terragrunt is required
only for client projects; the Docker image includes it.

Run these checks before opening a pull request:

```shell
tofu fmt -check -recursive 01-foundation 02-networking 03-compute modules examples

for d in 01-foundation/examples/test-local \
         02-networking/examples/test-local \
         03-compute/examples/test-local; do
  (cd "$d" && tofu init -backend=false -input=false && tofu validate)
done

cd examples/terragrunt-client
terragrunt hcl fmt --check
terragrunt hcl validate
```

## Contributing

Contributions are welcome. Read [CONTRIBUTING.md](CONTRIBUTING.md) for the
development workflow, module design rules, commit convention, local checks and
pull request checklist.

In short: branch from `main`, keep the module contract explicit, update the
documentation, run the development checks, and never commit credentials or
state files. Breaking module changes require a major version bump.

## Provider compatibility

All source modules require `bpg/proxmox` in the tested range:

```hcl
version = ">= 0.116.0, < 1.0.0"
```

- **Lower bound**: `02-networking` works around a provider 0.116.0 bug
  (`dhcp_range` objects read straight from a `for_each` value are seen as
  "unknown"; see the NOTE in `02-networking/main.tf`) — older versions are
  untested against that workaround.
- **Upper bound**: a provider `1.0.0` may carry breaking changes; bump it
  deliberately after validating a scenario run.

OpenTofu `>= 1.8.0` everywhere (`check` blocks, `optional()` object types).

## Versioning

Modules are consumed by Git tag. `main` is the development branch; releases are
immutable tags:

```shell
git tag -a vX.Y.Z -m "vX.Y.Z"
git push origin vX.Y.Z
```

Client projects pin `?ref=v1.0.0-rc1` and bump it deliberately — each release is
described in [CHANGELOG.md](CHANGELOG.md). See
[docs/terragrunt.md](docs/terragrunt.md#pinned-git-tags-mandatory) for the
upgrade procedure.
